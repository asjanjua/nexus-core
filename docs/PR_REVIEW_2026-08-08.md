## 3. PR #13 — db-check error suppression and PGlite tests

**Files:** `scripts/db-check.mjs`, `tests/db-check.test.ts`, `render.yaml`, `docs/ENGINEERING_GUARDRAILS.md`

### What is good

The core fix is correct and well-reasoned. Narrowing the bare `catch {}` to `error?.code === "42P01"` and re-throwing everything else is exactly right: previously an `ECONNREFUSED` reported as "run all migrations," which is the worst possible advice during an incident. Detecting drift in *both* directions is the right model, and the 2026-08-05 production incident is documented in the code rather than in someone's head. Using `process.exitCode` instead of `process.exit()` so both drift classes report in one run is a nice touch.

### 3.1 CRITICAL — the tests do not test the shipped code

`tests/db-check.test.ts` lines 82 to 119 reimplement `migrationState` inside the test file. There is no `import` of `db-check.mjs` anywhere in the suite.

The file is candid about it:

> "db-check.mjs is an ESM script (not a module exporting symbols), so migrationState is not importable. The test reproduces the logic inline rather than requiring a refactor... This is deliberate: the test IS the specification."

That justification does not hold. A test that asserts against a copy of the implementation is a tautology. It provides zero regression protection on `db-check.mjs`, and the ~7.4 seconds of PGlite startup buys nothing but confidence theatre. PR #14 then made it worse: it changed the *test's* error narrowing to a `typeof`/`in` guard while the shipped script still uses `error?.code`, so the two have already begun to diverge one commit after landing.

The stated blocker is a 15-line fix.

```bash
cat <<'EOF' > apps/mission-control/scripts/migration-state.mjs
import path from "node:path";
import { readdir } from "node:fs/promises";
import { fileURLToPath } from "node:url";

export const MIGRATIONS_DIR = path.join(
  path.dirname(fileURLToPath(import.meta.url)),
  "..",
  "db",
  "migrations"
);

export async function migrationState(pool, dir = MIGRATIONS_DIR) {
  const onDisk = (await readdir(dir)).filter((f) => f.endsWith(".sql")).sort();

  let applied = [];
  try {
    const { rows } = await pool.query("SELECT id FROM _nexus_migrations ORDER BY id");
    applied = rows.map((r) => r.id);
  } catch (error) {
    // 42P01 = undefined_table. Genuine "nothing has ever run here."
    if (error?.code === "42P01") {
      return { appliedCount: 0, latestApplied: null, pending: onDisk, appliedNotOnDisk: [] };
    }
    throw error;
  }

  const appliedSet = new Set(applied);
  const diskSet = new Set(onDisk);
  return {
    appliedCount: applied.length,
    latestApplied: applied[applied.length - 1] ?? null,
    pending: onDisk.filter((f) => !appliedSet.has(f)),
    appliedNotOnDisk: applied.filter((id) => !diskSet.has(id))
  };
}
EOF
```

Then `db-check.mjs` imports it, and the test deletes its duplicate and imports it too. The `dir` parameter is a bonus: it lets the test use a fixture directory instead of coupling every assertion to the real migrations folder.

### 3.2 MEDIUM — no timeout on a script that gates deploys

`new Pool({ connectionString })` sets neither `connectionTimeoutMillis` nor `statement_timeout`. `db:check` is a CI and runbook gate. Against a wedged database it hangs until the CI job's own timeout, which is a much noisier failure than a clean non-zero exit.

```js
const pool = new Pool({
  connectionString: normalizeDatabaseUrl(dbUrl),
  connectionTimeoutMillis: 10_000,
  statement_timeout: 15_000,
});
```

`db-migrate.mjs` has the same gap.

### 3.3 MEDIUM — no checksum drift detection

`_nexus_migrations` stores `id` only. Editing an already-applied migration file is invisible to both `db:migrate` (it skips on id) and `db:check` (the id set still matches). Given the whole point of the PR is "the database and this checkout agree," id equality is a weaker claim than the docs imply.

Suggested: add a `checksum TEXT` column, populate on apply, and have `db:check` report a third drift class, `modifiedAfterApply`. This is a small migration plus about 10 lines. It closes the one drift direction the PR does not cover.

### 3.4 LOW — sort collation mismatch

`db-check.mjs` sorts on-disk files with JS `.sort()` (UTF-16 code unit order) but reads applied ids with SQL `ORDER BY id` (database collation, typically `en_US.UTF-8`, which ignores punctuation differently). `db-migrate.mjs` uses a third ordering, `localeCompare`. Only `latestApplied` is affected — the `pending` and `appliedNotOnDisk` sets are order-independent — so it is cosmetic today. Make it deterministic anyway: `SELECT id FROM _nexus_migrations ORDER BY id COLLATE "C"`, and use the same comparator in all three places.

### 3.5 LOW — `process.exit(1)` skips the `finally`

In the catch block, `process.exit(1)` runs before `finally { await pool.end() }` can complete. Harmless because the process is terminating, but the comment on the `finally` ("always close the pool") is not accurate. Set `process.exitCode = 1` and let the `finally` run.

### 3.6 LOW — test 2 breaks on an empty migrations directory

`const halfway = Math.floor(allFiles.length / 2)` gives 0 when there are 0 or 1 files, making `applied` empty and `expect(state.latestApplied).toBe(applied[applied.length - 1])` compare `null` against `undefined`. Only bites on a fresh repo, but it makes the suite dependent on real directory contents in a way it does not need to be. The `dir` parameter from 3.1 solves this.

## 5. PR #11 — connector shared utilities (Devin AI)

**Files:** 46 changed, +1161 / −1776. The largest and highest-risk PR in the set.

Net deletion of 615 lines across 13 connector routes is a genuinely good refactor, and `tests/connector-shared.test.ts` (19 tests) covers the extracted helpers. Four defects survived.

### 5.1 HIGH — concurrent refresh can permanently brick a connector

`getValidConnectorAuth` in `lib/connectors/shared/access-token.ts` has no lock. Two requests arriving after expiry both see a stale token, both call `refreshAccessToken(refreshToken)` with the same refresh token, and both write back.

Microsoft (SharePoint, Outlook Mail) and QuickBooks all use **rotating, single-use refresh tokens**. The second call therefore fails, and worse, the winner's write can be overwritten by the loser's error path or by an interleaved `upsertConnector`. The connector ends up holding a refresh token the provider has already retired, and the only recovery is a manual reconnect by the customer.

This is not theoretical for you — ingest routes and cron sync fire concurrently by design.

The correct fix at your scale is a Postgres advisory lock around the refresh, since you already have the connection:

```ts
// Serialise refresh per (workspace, connector). hashtext gives a stable int4
// per key; pg_advisory_xact_lock releases automatically at transaction end.
const lockKey = `connector-refresh:${workspaceId}:${type}`;
await repository.withAdvisoryLock(lockKey, async () => {
  // Re-read credentials INSIDE the lock — another request may have
  // already refreshed while we waited.
  const fresh = await repository.getConnectorCredentials(workspaceId, type);
  if (isFresh(fresh?.obtainedAt, fresh?.expiresIn)) return fresh.accessToken;
  // ... perform refresh
});
```

An in-process promise cache (`Map<key, Promise<...>>`) is a cheaper 80% fix and worth doing today, but it only dedupes within one Node instance. On Render with more than one instance you still need the advisory lock.

### 5.2 MEDIUM — `decodeDownloadedText` misclassifies binary files (verified)

```ts
const text = buffer.toString("utf-8");
return text.includes("\0") ? buffer.toString("base64") : text;
```

`Buffer.toString("utf-8")` never throws — invalid bytes become U+FFFD replacement characters. So the `catch` branch is dead code, and any binary file that happens to contain no `0x00` byte is stored as mojibake text.

Verified with a JPEG header (`FF D8 FF E0 10 4A 46 49 46 C3 B1 FE`, no NUL byte):

```
result: "����JFIFñ�"    ← stored as evidence text
replacement chars: 5
```

For an evidence platform this is a correctness problem, not cosmetics: corrupted content gets hashed, embedded, and surfaced as citable evidence.

```ts
export function decodeDownloadedText(buffer: Buffer): string {
  const text = buffer.decodeUtf8Strict?.() ?? buffer.toString("utf-8");
  // A NUL byte, or more than 1% replacement characters, means these bytes
  // are not text. toString("utf-8") never throws, so the ratio is the only
  // signal available.
  const replacements = (text.match(/�/g) ?? []).length;
  const looksBinary =
    text.includes("\0") || replacements > Math.max(1, text.length * 0.01);
  return looksBinary ? buffer.toString("base64") : text;
}
```

Better still, use the `content-type` the provider already gave you as the primary signal and keep the heuristic as a fallback.

### 5.3 MEDIUM — `tenantIdForWorkspace` uses an unanchored replace (verified)

```ts
return workspaceId.replace("workspace-", "tenant-");
```

`String.replace` with a string pattern replaces the first occurrence *anywhere*, not a prefix. Verified:

| Input | Output | Correct? |
|---|---|---|
| `workspace-abc` | `tenant-abc` | yes |
| `acme-workspace-1` | `acme-tenant-1` | no |
| `tenant-x` | `tenant-x` | silently passed through |
| `ws-workspace-workspace-2` | `ws-tenant-workspace-2` | no |

The single test (`connector-shared.test.ts:261`) only covers the happy prefix case, and PR #8 explicitly added a commit titled *"document why the tenantId expectation pins current behaviour"* — the smell was noticed and pinned rather than fixed.

Tenant id derivation is a **data-isolation boundary**. A silent pass-through on an unexpected id shape is the kind of thing that ends up cross-posting one client's evidence into another's tenant. Fail loudly:

```ts
export function tenantIdForWorkspace(workspaceId: string): string {
  if (!workspaceId.startsWith("workspace-")) {
    throw new Error(`unexpected workspace id shape: ${workspaceId}`);
  }
  return `tenant-${workspaceId.slice("workspace-".length)}`;
}
```

If some ids legitimately do not carry the prefix, that needs to be an explicit, tested branch rather than an accident of `String.replace`.

### 5.4 MEDIUM — `connectorAppUrl()` falls back to localhost in production

```ts
export function connectorAppUrl(): string {
  return process.env.NEXT_PUBLIC_APP_URL ?? "http://localhost:3000";
}
```

With `NEXT_PUBLIC_APP_URL` unset, every OAuth callback redirects the customer to `http://localhost:3000/settings/connectors`. It looks like the app is broken, and it fires during the highest-intent moment in onboarding.

Note that `lib/connectors/outlook-mail.ts:57` already does this correctly (`if (!appUrl) throw new Error(...)`). The refactor extracted the weaker of the two patterns into the shared module. Mirror the outlook-mail behaviour, or fail closed only outside `isExplicitDevRuntime()`.

### 5.5 MEDIUM — OAuth state is not bound to the initiating session

`verifyConnectorState` proves the state was signed by this server and is under 10 minutes old. It does not prove the browser presenting the callback is the same browser that started the install.

The attack: an attacker starts an install for *their* workspace, captures the signed `state`, and gets a victim to complete the provider consent screen with that state. The victim's provider tokens land in the attacker's workspace. This is the standard OAuth login-CSRF / account-linking attack, and it matters more here than usual because the payload is a customer's SharePoint or QuickBooks credentials.

Two additions close it:

```ts
// 1. Bind the state to the initiating user, not just the workspace.
export type ConnectorStatePayload = {
  workspaceId: string;
  userId: string;
  nonce: string;
  ts: number;
};

// 2. At the callback, require the authenticated caller to match, and
//    burn the nonce so the state cannot be replayed inside its 10-minute window.
if (payload.userId !== ctx.userId) return redirectWithConnectorError(appUrl, "state_mismatch");
if (!(await consumeConnectorNonce(payload.nonce))) return redirectWithConnectorError(appUrl, "state_replayed");
```

Also worth hardening: `verifyConnectorState` casts the parsed JSON to `ConnectorStatePayload` without validating shapes. A payload missing `ts` yields `Date.now() - undefined === NaN`, and `NaN > STATE_MAX_AGE_MS` is `false`, so the expiry check passes. Only reachable with a valid signature today, but you already use zod everywhere — parse it.

### 5.6 LOW — refresh overwrites installer attribution

```ts
await repository.upsertConnector({ workspaceId, type, installedBy: "token-refresh", ... });
```

Every successful token refresh replaces the original `installedBy` with the literal `"token-refresh"`. For a platform whose value proposition is auditable evidence, losing "who connected this data source" is a real gap. Preserve `creds.installedBy` (or the connector record's) and record the refresh in a separate `lastRefreshedAt` field.

### 5.7 LOW — `readStreamToBuffer` has no size cap

An oversized provider download accumulates unbounded chunks in memory before any validation runs. Add a `maxBytes` parameter that aborts the reader once the running total is exceeded, mirroring the caps PR #10 added for zip imports.

## 6. PR #10 — security scan fixes (Devin AI)

Strong PR. Signing unsubscribe tokens, replacing `NODE_ENV !== "production"` with the explicit `isExplicitDevRuntime()` allowlist, deleting `verifyLoginCredentials` (confirmed: zero remaining references), and refusing to seed a default `admin` password are all correct and correctly reasoned.

### 6.1 HIGH — signed tokens invalidate every unsubscribe link already in the wild

`buildUnsubscribeToken` changed from `base64url(workspaceId:email)` to `base64url(...).hmac`, and `decodeUnsubscribeToken` now rejects anything without a valid signature. Every unsubscribe link in every brief email already delivered is now dead.

Two problems. Commercially, recipients who try to unsubscribe and fail will mark the mail as spam, which damages your sending domain's reputation. Legally, an unsubscribe mechanism that does not function is a compliance exposure under CAN-SPAM and under GDPR Article 21 for the EU recipients in your GCC and Pakistan client base.

The PR fixes a real forgery hole, so the change is right. The rollout is what is missing. Add a bounded legacy path:

```ts
export function decodeUnsubscribeToken(token: string): [string, string] | null {
  try {
    if (!token.includes(".")) {
      // Legacy unsigned token, issued before 2026-07-28. Accepted until
      // LEGACY_UNSUBSCRIBE_UNTIL so links in already-delivered mail keep
      // working. Unsigned means forgeable, and the only thing a forgery can
      // do is unsubscribe an address the attacker already knows — an
      // acceptable trade for a fixed window. Delete this branch after the date.
      if (Date.now() > Date.parse("2026-10-31")) return null;
      const decoded = Buffer.from(token, "base64url").toString("utf-8");
      const idx = decoded.indexOf(":");
      return idx > 0 ? [decoded.slice(0, idx), decoded.slice(idx + 1)] : null;
    }
    // ... existing signed path
  } catch { return null; }
}
```

Separately: `signHmacHex` derives from `AUTH_SECRET`. Rotating `AUTH_SECRET` will silently kill all outstanding unsubscribe links *and* all connector OAuth states. Use a purpose-derived subkey (`HKDF(AUTH_SECRET, "unsubscribe-v1")`) so the two rotation lifetimes are independent.

### 6.2 MEDIUM — the zip-bomb guard depends on a JSZip private field

```ts
function declaredUncompressedSize(entry: JSZip.JSZipObject): number | null {
  const data = (entry as JSZip.JSZipObject & { _data?: { uncompressedSize?: unknown } })._data;
  return typeof data?.uncompressedSize === "number" ? data.uncompressedSize : null;
}
```

`_data` is not part of JSZip's public API, and `package.json` pins `"jszip": "^3.10.1"` — a caret range. Any minor release that renames or restructures `_data` makes this return `null`, at which point the guard is skipped entirely and the only remaining defence is the *post*-inflation check, by which point the bomb is already resident in memory.

The failure is silent, which is the worst property a security control can have. Two mitigations, do both:

1. Pin exactly: `"jszip": "3.10.1"`.
2. Add a test that asserts the field is still readable, so a dependency bump turns into a red build rather than a silently disabled control:

```ts
it("can still read the declared uncompressed size from the JSZip entry", async () => {
  const zip = new JSZip();
  zip.file("a.md", "x".repeat(5000));
  const loaded = await JSZip.loadAsync(await zip.generateAsync({ type: "nodebuffer" }));
  expect(declaredUncompressedSize(loaded.files["a.md"])).toBe(5000);
});
```

If `declaredUncompressedSize` returns `null` for an entry, consider rejecting the archive rather than falling through.

### 6.3 MEDIUM — the 413 check runs after the body is already buffered

```ts
const form = await request.formData();          // ← whole body in memory here
const file = form?.get("file");
if (file.size > MAX_IMPORT_ARCHIVE_BYTES) return fail("file_too_large", 413);
```

By the time `file.size` is readable, `formData()` has already materialised the upload. The 413 is honest to the caller but buys no resource protection. Check `content-length` first and reject before touching the body:

```ts
const declared = Number(request.headers.get("content-length") ?? 0);
if (declared > MAX_IMPORT_ARCHIVE_BYTES) return fail("file_too_large", 413);
```

Belt and braces: enforce the cap at the edge too (Render or your reverse proxy body-size limit), since a client can lie about `content-length`.

### 6.4 LOW — no aggregate uncompressed cap

Per-note (1 MB) and note-count (1000) caps exist, but 1000 × 1 MB = 1 GB of decompression work and database writes from a single upload. Peak memory is bounded because entries are processed sequentially, so this is a throughput and cost concern rather than an OOM. Add a running `totalUncompressed` counter and abort at, say, 100 MB.

### 6.5 LOW — `isExplicitDevRuntime` is duplicated with no drift guard

`lib/security-headers.ts` re-declares the function because it runs in edge middleware and cannot import `node:crypto`. The comment explains the constraint honestly. Add a test that asserts both implementations agree across `"production"`, `"development"`, `"test"`, and `undefined`, so the two cannot drift.

### 7.1 HIGH — `context.extra` is accepted and silently discarded

> **CORRECTION (2026-08-08, during remediation).** The observation is right; the
> recommended fix was **wrong and actively unsafe**. Dropping `extra` was not an
> oversight — it is a deliberate PII decision, pinned by
> `tests/audit-write-failure.test.ts` ("does not log caller-supplied extra
> payloads, which can carry PII") with a caller passing
> `{ email: "someone@example.com", secret: "tok_live_abc" }`.
>
> The patch below was applied, and that test failed on the full suite run. The
> email would have been caught by the scrubber; `tok_live_abc` would have gone
> straight into the log.
>
> Resolved with an allowlist instead: `connectorType`, `feature`, `attempt` and
> similar operational keys are logged; anything else is dropped and reported as
> `extraOmitted=N`. Both properties are now tested in
> `tests/observability-report.test.ts`. The lesson: a value that looks dropped
> by accident may be dropped on purpose — check for a test asserting the
> current behaviour before calling it a bug.

`lib/observability/sentry.ts` types `extra?: Record<string, unknown>` on `ReportContext`, but `report()` never reads it:

```ts
const parts = [
  `[observability] ${context.errorType}`,
  `route=${context.route}`,
  context.workspaceId ? `workspace=${context.workspaceId}` : null,
  `detail=${detail}`,
].filter(Boolean);
```

**12 call sites** currently pass `extra` — `{ connectorType: type }`, `{ feature }`, and others. None of it reaches the log. During an incident you will read this code, see `extra: { connectorType: type }` at the call site, and reasonably assume the connector type is in your Render logs. It is not.

```ts
function report(level: "error" | "warn", detail: string, context: ReportContext): void {
  // Log-injection guard: error messages can carry newlines, which would
  // otherwise split one event into several lines in Render's log stream.
  const oneLine = (s: string) => s.replace(/[\r\n]+/g, " ").slice(0, 500);
  const extra = Object.entries(context.extra ?? {})
    .map(([k, v]) => `${k}=${oneLine(String(v))}`);

  console[level]([
    `[observability] ${context.errorType}`,
    `route=${context.route}`,
    context.workspaceId ? `workspace=${context.workspaceId}` : null,
    ...extra,
    `detail=${oneLine(detail)}`,
  ].filter(Boolean).join(" "));
}
```

Two related points on the same file:

- **The name lies.** The module is `observability/sentry.ts`, the functions are `capture*`, and the header explains at length that no Sentry reporting happens. Someone will page you at 3am asking why nothing is in Sentry. Rename to `observability/report.ts` and `reportHandledError` / `reportDegradedState`, or wire up the actual Sentry transport.
- **PII in `detail`.** The header states payloads are excluded to keep customer PII out of plaintext logs. But `messageOf(err)` returns raw error messages, and Postgres errors routinely echo parameter values — `duplicate key value violates unique constraint ... Key (email)=(ceo@client.com) already exists`. Given PDPL and GDPR obligations across your client base, either scrub known patterns or truncate more aggressively.

### 7.2 HIGH — the fail-open access result is cached

```ts
const record = await repository.getWorkspaceStatus(workspaceId).catch(/* report */ () => null);
const result = record ? evaluateWorkspaceAccess(record) : { blocked: false, reason: null };
accessCache.set(workspaceId, { ...result, expiresAt: Date.now() + ACCESS_CACHE_TTL_MS });
```

A single transient DB error produces `{ blocked: false }` and then **caches it for the full TTL**. A suspended or expired workspace stays served for the whole window off one blip. The PR touched this exact function and added the correct observation ("a sustained failure means suspended and expired workspaces are being served as if they were active") without closing the amplification.

```ts
if (!record) {
  // Fail open, but do NOT cache the fallback — one transient error should
  // not keep a suspended workspace live for the full TTL.
  return { blocked: false, reason: null };
}
const result = evaluateWorkspaceAccess(record);
accessCache.set(workspaceId, { ...result, expiresAt: Date.now() + ACCESS_CACHE_TTL_MS });
return result;
```

### 7.3 MEDIUM — unbounded report volume on sustained failures

`generateEmbedding` calls `captureDegradedState` on every non-ok response. During a bulk ingest with OpenAI degraded, that is one log line per chunk — tens of thousands of lines, and a proportional bill once you connect a real Sentry DSN. The same applies to `getConnectorCredentials` emitting `connector_credentials_undecryptable` on every cron poll of a broken connector.

The PR already has the right pattern for this — `reportedMissingKey` reports the unset-key case exactly once. Generalise it:

```ts
const lastReported = new Map<string, number>();
const REPORT_COOLDOWN_MS = 60_000;

function shouldReport(key: string): boolean {
  const now = Date.now();
  if ((lastReported.get(key) ?? 0) > now - REPORT_COOLDOWN_MS) return false;
  lastReported.set(key, now);
  return true;
}
```

Key on `errorType:route:workspaceId`. Cap the map size so it cannot grow unboundedly across workspaces.

### 7.4 LOW — `route` naming is inconsistent

Three conventions are in use: `lib/api-auth.checkWorkspaceAccess`, `repository.getStripeCustomerId`, `connectors.shared.getValidConnectorAuth`. Log grouping and alerting both depend on this field being predictable. Pick one — `module.function` with the `lib/` prefix stripped is the most common — and normalise.

## 10. Cross-cutting themes

**1. Tests that verify the test rather than the code.** PR #13's duplicated `migrationState` is the clear case; PR #8's most heavily-mocked files are a milder version. Add a review question: *does this test import the shipped symbol?*

**2. Silent degradation of security controls.** Three separate controls fail open without noise: the JSZip `_data` guard (6.2), the fail-open access cache (7.2), and `tenantIdForWorkspace`'s pass-through (5.3). A control that can be disabled by a dependency bump or a transient error, without anyone noticing, is not a control. Every one of them should either throw or emit a distinct alert when it cannot function.

**3. Parallel agent branches do not see each other.** PR #11 extracted the weaker of two existing `NEXT_PUBLIC_APP_URL` patterns into shared code while the stronger one sat in `outlook-mail.ts`. When fanning out agents, either serialise refactors or brief every agent with the codebase's existing best-in-class pattern for whatever it is extracting.

**4. The pre-merge gate is incomplete.** PR #14 exists solely because lint did not run before #13 merged. That is a 5-line CI fix.
